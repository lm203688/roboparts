## 一、板块定位与边界

**一句话**：RoboParts 的「心脏」——把「这两个零件能不能装 / 能不能共装 / 能不能互换」变成可核验的三态结论（能 / 不能 / 不知道）。

**三套引擎（必须分开陈述，不可混用）**：

| 引擎 | 位置 | 维度 | 对外通道 |
|---|---|---|---|
| **产品层四维** | `_lib/compat_engine.js` | protocol / electrical / mechanical / software | `/api/compatibility`、`/mcp` 的 `check_compatibility` |
| **研究层三轴** | `scripts/compose_engine.py` | mechanical / electrical / signal（三态 fail-closed） | `compose_semantics.json` / `compose_frontier.json` |
| **共装层三段** | `_lib/co_mount_engine.js` + `co_mount_engine.py` | mount_fit + port_budget + signal_complementary | `/api/co-mount`、`check_co_mount` |

**实测规模**：产品层四维（含 `scoreBreakdown` 多因子加权 0.35/0.25/0.25/0.15）；共装层线上 `/api/co-mount` 实测 171 + 126 + 63 = 360 对；研究层 `compose_semantics` 判定对空间 214,840，其中 composed 262（0.1%）。

## 二、流程审计

### 2.1 流程是否合理

**这是全仓工程纪律最强的一个板块。** 引擎文件头逐条记录了「为什么要这样写」，且每条都有事故依据：

| 设计决策 | 合理性 | 仓内证据 |
|---|---|---|
| 单一实现（SSOT） | ✅ 极强 | `compat_engine.js` 头部：「同一问题给出三个不同答案且不会有任何报错——这正是假绿的高阶形态」；`regression.py L1.16` 守护「不得自带本地副本」 |
| 三态 fail-closed | ✅ 极强 | 不可判定 → 判 `unknown`，不判通过；`overall=null` 时分数一律 null，不给 0 也不给 100 |
| 词表按词边界匹配 | ✅ 强 | `io-link` / `powerlink` 都含 `lin`，裸 `includes` 会造出假绿 |
| 身份键纪律 | ✅ 强 | `mount_type` 曾被当身份键 → 假绿，已修；`MECH_IDENTITY_FIELDS = ['standard','flange']` |
| 侧别区分 | ✅ 强 | 「机器人侧」≠「工具侧」；只声明工具侧时判「判不了」而非 false（假红） |
| 归一化只做词法 | ✅ 强 | `normalizeMechToken` 只统一大小写/空白/连字符，不做语义合并 |
| 显式登记优先于公理 | ✅ 强 | reflexivity 曾无条件应用，静默覆盖显式登记，已修 |
| 「不知道」的成因分类 | ✅ 强 | 区分「厂商未声明」/「我方词表不认识」/「只给非决定性属性」/「侧别不齐」四种 |

> **判断**：流程**合理**，且达到学术级严谨。这是全仓最值钱的资产。

### 2.2 是否全面走通

| 子链路 | 状态 | 说明 |
|---|---|---|
| 页面 → 端点 → 结果 | ✅ 通 | `bom-checker` / `co-mount` / `compatibility-viewer` 线上可用 |
| REST ↔ MCP 一致 | ✅ 通 | 两通道 import 同一引擎；「双引擎口径桥接一致」闸门守护 |
| 判定 → 证据链 | ✅ 通 | 共装层有 `coMountEvidence`（判定层溯源）；产品层有 `mechanicalEvidence` 分侧证据 |
| 判定 → 可解释 | ✅ 通 | `scoreBreakdown` 给权重分解；`inconclusiveNote` 给「为什么判不了」 |
| **判定 → 用户可理解** | ⚠️ **半通** | 结论是 `compatible` / `incompatible` / `unknown` 这类词汇，**普通用户需要翻译**；copilot 是翻译层但依赖外部 LLM |
| **判定 → 真实使用** | ❌ **断** | `demand-signal` 实测 `cross_brand_compat_engine_users: 0`；无人调用该能力 |

> **结论**：引擎内部**完全走通**，且严谨度极高。断点在两端：**入口太专业（用户看不懂）**、**出口无人用（没有真实提问）**。

### 2.3 是否符合人类使用习惯

| 用户真实问法 | 引擎的答法 | 契合度 |
|---|---|---|
| 「这两个能装吗？」 | `check_compatibility(a,b)` → 四维裁决 | ✅ 对得上 |
| 「为什么不能装？」 | `inconclusiveNote` + 证据链 | ✅ 好 |
| 「我要买哪个？」 | ❌ 不是本板块职责（属选型） | — |
| 「我手上这个夹爪能配哪些臂？」 | 需要 `check_co_mount(host)` 且需知道 host id | ⚠️ **入口门槛高**：用户不知道 `HUB-030` 这种内部 id |
| 「我英文不好，能大白话问吗？」 | copilot 页面（依赖外部 LLM 后端） | ⚠️ 依赖外部可用性 |

> **关键 UX 缺口**：**入口要求用户知道内部实体 id**（`ACT-028`、`HUB-030`）。真实用户脑子里是「Robotiq 2F-85」和「UR5e」，不是我们的 id。**缺一个「说人话 → 定位 id → 判定」的桥。**

## 三、市场竞品与市场需求比较

### 3.1 竞品对照

| 竞品 | 它的做法 | 强项 | RoboParts 的差异 |
|---|---|---|---|
| **roboxdb** | 浏览器内 MuJoCo 物理验证 | **物理层验证**（几何/碰撞真实跑） | RoboParts 是**声明层判定**（基于 datasheet 事实），不跑物理 |
| **TraceParts / GrabCAD** | 只提供模型，不判兼容 | 模型量大 | RoboParts 有判定无模型 |
| **各厂商自己的选型工具**（Robotiq / OnRobot / Universal Robots） | 只判自家产品 | 准确 | **不跨品牌**——而跨品牌正是 RoboParts 的唯一生态位 |
| **ROS 生态（URDF 检查器）** | 语法/结构校验 | 免费 | 只查 URDF 语法，不查物理兼容 |

> **生态位判断**：RoboParts 的独特位置是「**跨品牌、声明层、可溯源、三态诚实**」。roboxdb 占了「物理验证」，TraceParts 占了「模型分发」，两者都不做「跨品牌声明层判定」。**这个位置目前没有直接对手。**

### 3.2 市场需求实测

- `demand-signal.json`：`explicit_compatibility_pain: 0`、`cross_brand_compat_engine_users: 0`。
- `compose_frontier.json` 的 `co_mount_theorem` 是一个**强假说（非已证定理）**：「cobot EOAT 器件族 composed 恒为 0 很可能不是数据缺口，而是关系类型错配」——即用户真正需要的是**共装**，而不是**点对点直连**。
- 这是一个**极重要的产品洞察**：用户问的问题类型，与引擎默认回答的问题类型**错位**。

> **判断**：引擎的能力与真实需求之间存在**问题类型错配**——引擎擅长答「能不能直连」，用户实际想问「能不能共装/互换」。共装层已建，但被埋在 `/api/co-mount`，没有成为主入口。

## 六、诚实边界

1. 本板块为**声明层判定**，非物理验证。不构成「装得上」的物理保证——这是项目自己反复声明的边界，也是与 roboxdb 的正当划界。
2. `compose_frontier.co_mount_theorem` 是**强假说**（9 个已判结果样本），样本量不足以称为定理。
3. 本仓无 ISO 原文，标准映射不构成符合性声明。
4. 引擎的严谨性不等于用户价值——**当前最大风险不是判错，是没人用**。
