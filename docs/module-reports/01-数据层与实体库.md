## 二、流程审计

### 2.1 流程是否合理

**链路**：采集（`data_acquisition` / OSS BOM / 厂商官域）→ 入库（`entities.json` 单一真相源）→ 派生（semantic_index / croissant / provenance / derived_features）→ 分发（REST + MCP + 数据集双平台）。

| 环节 | 是否合理 | 实测证据 |
|---|---|---|
| 单一真相源 | ✅ 合理且严格 | 全仓数字均由 `inject_readme_stats.py` 从 `entities.json` 现算，禁手改；「公开清单现算」闸门守护 |
| 三态溯源 | ✅ 合理 | `source_tier` + `confidence` + `last_verified`；「无出处不入库」写进 `CONTRIBUTING.md` |
| 派生层 | ✅ 合理 | provenance / croissant / semantic_index 均为自动派生，非手写 |
| 分发层 | ✅ 合理 | 双平台同步（HuggingFace + ModelScope）+ Croissant 元数据 |
| **采集层** | ⚠️ **是短板** | 机械接口声明率四个月停在 16.2%（`mechanical_interface_coverage.fill_pct`），采集靠人工 + 少量 OSS BOM |

> **判断**：流程设计**合理**，且远高于同类项目（多数零件库连溯源都没有）。唯一不合理处是**采集环节的产能**——设计了正确的入口（贡献表单、BOM 反喂、spec-declare），但产能没有兑现。

### 2.2 是否全面走通

| 子链路 | 状态 | 断点 |
|---|---|---|
| 页面 → 端点 | ✅ 通 | `data-hub.html` 调 `/api/entities.json`、`/api/stats` 正常 |
| 端点 → 数据 | ✅ 通 | 线上 `/api/entities.json` = 200，868 实体与本地一致 |
| 搜索 → 结果 | ✅ 通 | 关键词搜索 + 语义搜索（`semantic_index.json`）双通道 |
| 实体详情 → 付费墙 | ✅ 通 | `/api/entity/{id}` 用 `paywall.js` 统一投影，付费字段黑名单 10 项 |
| **数据 → 下游消费** | ⚠️ **半通** | 数据能被 REST/MCP 读到，但**没有下游产品真正消费它**（选型、设计、BOM 各自独立） |
| **数据 → 外部引用** | ❌ **断** | 无第三方项目引用该数据集；HuggingFace/ModelScope 下载量为 0 级 |

> **结论**：数据层内部**全面走通**，但「走出去」这一步是断的——它是「自产自销」的闭环。

### 2.3 是否符合人类使用习惯

目标用户有四类：**工程师**（要孔位/扭矩/协议）、**采购**（要价格/供货）、**开源构建者**（要能直接用的 BOM）、**Agent**（要机读）。

| 用户习惯 | 本板块的入口 | 契合度 |
|---|---|---|
| 工程师「按孔位筛零件」 | 无。只有按品类 + 关键词 + 语义搜索 | ❌ **缺**。这是工程师最刚性的筛选维度 |
| 工程师「对比 2–3 个候选」 | parts-viewer 有 3D 预览，但无并排对比 | ⚠️ 弱 |
| 采购「按价格/供货筛」 | 价格是**付费字段**（`price_range` 在 `PREMIUM_FIELDS`） | ⚠️ 免费用户看不到 |
| 构建者「直接拿一份能跑的 BOM」 | `reference-builds.html`（参考构型）+ urdf-library | ✅ 较好 |
| Agent「机读事实」 | `/api/entities.json` + MCP `search_components` | ✅ 强 |

> **关键 UX 缺口**：**没有「按机械接口筛选」的入口。** 而项目自己承认「最大的缺口是机械接口声明率」——入口与缺口不匹配：缺的是数据，但也没给用户一个「我要找 ISO 9409-1-50-4-M6 的夹爪」的入口。

## 三、市场竞品与市场需求比较

### 3.1 竞品对照

| 竞品 | 定位 | 强项 | 相对 RoboParts |
|---|---|---|---|
| **TraceParts / GrabCAD** | 通用零件 CAD 库 | 海量 3D 模型 + 厂商直供 | 它们有**模型**无**兼容判定**；RoboParts 有判定无模型 |
| **Octopart / Findchips** | 电子元件搜索 | 实时库存 + 价格聚合 | 电子域，不覆盖机械/机器人 |
| **roboxdb** | 机器人零件库 + 浏览器内 MuJoCo 物理验证 | 物理验证 + source-backed specs | 直接重叠；它的物理验证领先，RoboParts 的判定深度领先 |
| **OpenLoong / OpenLET（2026 国内开源社区）** | 人形机器人开源社区 + 数据集 | 社区规模（2 万+ 开发者） | 它们有**社区**无**判定引擎**；RoboParts 反之 |
| **Hugging Face datasets** | 通用数据集托管 | 分发渠道 | RoboParts 已上架，但无差异化 |

### 3.2 市场需求实测

- 仓内 `api/demand-signal.json`（scan_date 2026-08-28）实测：**`real_query_count: 0`、`explicit_compatibility_pain: 0`、`cross_brand_compat_engine_users: 0`**。
- 这意味着：**外部真实社区里，没有人在问「这两个零件能不能配」**——至少当前监听通道（GitHub / ROS Discourse / Stack Exchange）没有捕捉到。
- 但 `can_answer_today` 自述「跨品牌兼容类提问多数仍答不出」——**需求与能力都在低位**。

> **判断**：数据层面对的不是「需求旺盛但供给不足」，而是「**需求本身未被唤醒**」。这解释了为什么数据量增长没有带来使用量增长。

## 四、最新开源技术融合评估

| 开源技术 / 标准 | 2026 状态 | 接入点（已有资产） | 融合形态 | 拒绝条件 |
|---|---|---|---|---|
| **ISO 22166-201 模块通用信息模型**（2026 发布） | 国际标准，与 GB/T 43210 系列对应 | `entities.json` 字段表 | 把字段表对齐 201 的信息模型条目，产出 `iso22166-201-map.md` | 无原文 ⇒ 只做方向性映射，不称「符合」 |
| **ISO 22166-202 软件模块信息模型**（2025） | 国际标准 | `llms.json` / `robot_ai_models.json` | AI 模型实体对齐 202 的软件模块信息模型 | 同上 |
| **MinerU 2.5-Pro**（开源文档解析，Apache-2.0 衍生） | 2026 活跃 | 采集环节 | VLM/OCR 从厂商 PDF 批量抽结构化属性（已有 `vlm-extraction-pending.json` 队列） | 抽取结果 confidence < 0.7 不得进主库（已挂闸门） |
| **Croissant**（ML 数据集元数据标准） | 已采用 | `croissant.json` | 保持，扩展 entity 级 Croissant | — |
| **schema.org / JSON-LD** | 通用 | 页面 SEO | 为每个实体页注入 `Product` / `PropertyValue` JSON-LD | 不得引入虚假价格 |
| **RxDB 17 WebMCP**（2026 新增，Agent 直连数据） | 活跃 | 数据层 | 把实体库暴露为 WebMCP 可查询集合，让浏览器内 Agent 直接查 | 不得绕过 fail-closed 与付费墙 |
| **SPDX / OpenMDW-1.1** | 许可标准 | `DATA-LICENSE.md` | 数据许可机器可读化 | — |

> **首选融合**：**MinerU + VLM 抽取队列**。项目已有 `vlm-extraction-pending.json` / `vlm-extraction-approved.json` 与闸门，只差把「从厂商 PDF 抽属性」这一步做量产——这是**直接对治 16.2% 声明率**的技术。

## 六、诚实边界

1. 本板块数字全部现算自 `api/*.json`（2026-10-14），可复现。
2. 「机械声明率 16.2%」是项目自定的分母（applicable 500），换分母数字会变——项目已在 `mechanical_interface_coverage.note` 中声明此口径。
3. 竞品信息为联网核实时点快照，未逐工具实测。
4. 本报告不构成数据质量担保：仓内参数为厂商公开值，非本仓实测。
