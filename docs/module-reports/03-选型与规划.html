一、板块定位与边界

一句话：把「我要做一台人形机器人，给我一份能买、能装、能跑的清单」变成一条自动化的规划流水线。

四个子功能（彼此独立、无互调）：

子功能 页面 后端 做什么
场景选型 selection.html /api/selection/engine 按场景（humanoid/quadruped/robot_arm/amr/industrial）给五维加权推荐
构建规划 build-planner.html 复用选型 + BOM 选型 → BOM 与兼容性清单
组装模拟 assembly.html 前端 拖拽组装（智能家具式）
设计画布 designer.html 前端（three.js + URDFLoader） URDF 导入预览 + BOM + 一键 3D 打印 + 导出 STL/URDF/CSV

实测规模：选型引擎 1097 行，含 APPLICATION_WEIGHTS 场景权重、scoreActuator/Sensor/Chip 三套打分、analyzeCompatibility 兼容性分析；设计画布 4065 行（全仓最大页面），含 URDF 加载、关节控制、物料清单、3D 打印导出。

二、流程审计

2.1 流程是否合理

环节 是否合理 实测证据
场景 → 权重 ✅ 合理 APPLICATION_WEIGHTS 按场景配置扭矩/重量/协议/精度/功耗/可靠性优先级
需求 → 筛选 ✅ 合理 filterActuators/Sensors/Chips 按预算/扭矩/重量/电压/协议/ROS 过滤
筛选 → 打分 ✅ 合理 性能匹配 40% + 成本效益 30% + 生态兼容 20% + 成熟度 10%
打分 → 推荐 ✅ 合理 含理由（actuatorCompatNotes）与 TRL 估算（estimateTRL）
选型 → BOM ⚠️ 重复实现 build-planner 与 selection 各自有选型逻辑；bom/check 又有一套目录加载
选型 → 设计画布 ❌ 断 两者无互调：选型结果不能一键导入画布
设计画布 → 转接件 ❌ 断 画布发现孔位不匹配时，不能跳到 adapter-generator
计费 ⚠️ 需注意 选型每次消耗 2 积分（CREDIT_COST = 2），免费层无试用

判断：单点流程合理，但端到端流程断裂。这四个子功能本应是一条流水线（选型 → 规划 → 组装 → 设计 → 转接），实际是四个孤岛。

2.2 是否全面走通

子链路 状态
selection 页 → 引擎 → 结果表 ✅ 通（需积分或 key）
引擎 → 兼容性分析 ✅ 通
designer 导入 URDF → 3D 预览 ✅ 通（three.js + URDFLoader）
designer 导出 STL/URDF/CSV ✅ 通
选型结果 → designer ❌ 无入口
designer 不匹配 → adapter-generator ❌ 无入口
推荐反馈闭环 ⚠️ /api/recommend-feedback 存在，但无真实反馈数据
真实用户使用 ❌ 无证据

结论：每个子功能内部走通，跨子功能的流水线未走通。这是本板块最大的结构性缺陷。

2.3 是否符合人类使用习惯

真实工程师的工作流是：明确需求 → 选型 → 组 BOM → 查兼容 → 发现装不上 → 做转接件 → 出图/下单。

工作流步骤 本板块覆盖 契合度
明确需求 ✅ 场景选择器 ✅
选型 ✅ 五维推荐 ✅
组 BOM ✅ build-planner ✅
查兼容 ⚠️ 要跳去 bom-checker（另一板块） ⚠️ 跳转断
做转接件 ❌ 要跳去 adapter-generator（另一板块） ❌ 断
出图/下单 ⚠️ 画布能出图，下单在 order.html ⚠️ 弱

关键 UX 缺口：四个子功能之间没有「下一步」按钮。 用户选完型后，页面不会引导他去查兼容、做转接件、下单。人类习惯是「一条龙」，本项目给的是「四家店」。

三、市场竞品与市场需求比较

3.1 竞品对照

竞品 定位 强项 RoboParts 的差异
厂商选型工具（Thomson、KISSsoft、Max Jac） 单厂商选型 参数精准、含工程计算 只覆盖自家产品；RoboParts 跨品牌
TraceParts / GrabCAD 选型 目录检索 模型+规格 不做多因子推荐
OpenLoong / OpenLET 开源整机方案 提供参考构型 提供方案不做选型推荐
Onshape / Fusion 360 云 CAD 完整设计能力 无兼容判定；RoboParts 画布是「兼容感知」的
text-to-cad（earthtojake，8.3K star） Agent 技能，自然语言→CAD 生成能力强 它生成，RoboParts 判定；互补
JellyCAD 机器人可编程 CAD（Lua） 面向机器人 无兼容判定

生态位：RoboParts 的选型引擎独特在「跨品牌 + 兼容感知」——推荐的不只是「参数达标」的零件，而是「能和你已有零件装一起」的零件。这个组合目前无对手。

3.2 市场需求实测

  • demand-signal.json 的 real_query_count: 0 —— 没有捕捉到选型类真实提问。
  • 但项目自己产出了 22 篇技术文库（content/article-01~21），其中「膝关节执行器选型」「触觉传感器选型指南」「机器人边缘芯片选型」等正是选型需求——说明项目自己判断需求存在，但外部信号未验证。
  • 选型引擎消耗积分（2 分/次），免费用户无法试用——这是需求验证的阻碍：连试用门槛都高。

判断：需求可能真实存在（选型是机器人开发的刚需），但本板块没有任何免费试用入口，导致需求无法被验证。

五、提升方案

P0（不做则板块不成立）

# 动作 验收判据
1 串成流水线：selection → build-planner → designer → adapter-generator 之间加「下一步」入口，结果可传递 从选型到出图全程无需手抄；挂闸门断言各跳转存在
2 给免费试用额度：选型引擎首次免费（如 1 次），否则需求无法验证 匿名用户可跑通一次完整选型
3 消除重复实现：build-planner / selection / bom/check 的选型逻辑收敛为一处 同一输入给同一结果；挂闸门
