## 一、板块定位与边界

**一句话**：RoboParts 的「从判定走向解决」——两侧法兰孔位不一致时，自动生成一块可 3D 打印的转接板。

**实测能力**：
- 页面为**参数驱动**：选择侧 A / 侧 B 法兰 → 设定板厚与中心孔 → 浏览器内 three.js 实时 3D 预览 → 导出 **STL**（3D 打印）或 **.scad**（OpenSCAD 源文件）。
- 内置 ISO 9409-1 法兰预设：A20 / A31.5 / A40 / A50 / A63 / A80 / A100 / A160 / A250（含 PCD / 孔数 / 螺纹 / 沉孔 / 定位销）。
- 安装回填闭环：`/api/adapter-feedback`（POST 采集 / GET 回流为 `community_fit` 社区口碑）。

**实测发现（重要）**：
- `cad/` 目录下 **12 个文件全部是占位符**（内容为 `# Placeholder for cad\...step`，44–56 字节）。
- `3d/` 目录下 **7 个 STL 全部是占位符**（`# Placeholder for 3d\...stl`）。
- 即：**项目声称的「CAD 资产库」是空的**；转接件生成器本身靠参数在浏览器内实时生成几何（这部分是真的）。

## 二、流程审计

### 2.1 流程是否合理

| 环节 | 是否合理 | 实测证据 |
|---|---|---|
| 法兰参数预设 | ✅ 合理 | 预设采用「本库实测真实存在的 (PCD, 孔数, 螺纹)」，且注释明确「销孔属厂商自定义尺寸，无公开依据一律置 0，不得外推」——**纪律很好** |
| 几何生成 | ✅ 合理 | three.js 参数化生成 + STLExporter |
| 导出双格式 | ✅ 合理 | STL（打印）+ .scad（桌面二次编辑）——覆盖两类用户 |
| 安全提示 | ✅ 合理 | 页面列出 4 条装机红线（螺栓不得过长顶破油封 / 螺栓等级按原厂 / 定位销 / 不构成认证） |
| 安装回填闭环 | ✅ 设计合理 | bad 占比 ≥ 0.3 → `needs_review`；样本不足 → `insufficient_data`；**不自动改写兼容性**（守假绿纪律） |
| **几何正确性验证** | ❌ **缺** | 生成的转接板**没有任何几何校验**（孔位是否真的对得上、板厚是否与螺栓长度相容） |
| **CAD 资产** | ❌ **空** | `cad/` 与 `3d/` 全为占位符 |

> **判断**：**生成流程合理，但缺少「生成结果是否正确」的验证环节**，且声称的资产库是空的。这与项目在判定引擎上表现出的严谨度形成鲜明反差。

### 2.2 是否全面走通

| 子链路 | 状态 |
|---|---|
| 页面 → 选法兰 → 生成预览 | ✅ 通 |
| 生成 → 下载 STL | ✅ 通 |
| 生成 → 下载 .scad | ✅ 通 |
| 打印 → 安装 → 回填 | ⚠️ **链路存在但无样本**（KV 为空，无真实回填） |
| 回填 → 社区口碑 | ⚠️ 逻辑在，无数据 |
| **转接件 → 判定引擎联动** | ❌ 断：转接件生成器不知道「为什么需要转接」（不调用兼容判定） |
| **判定不匹配 → 转接件生成** | ❌ 断：`compatibility` / `bom-checker` 结果不能一键跳到这里并带参 |
| **cad/ 3d/ 资产被引用** | ❌ 占位符，未被有效引用 |

> **结论**：**「生成 → 下载」这条最短路径走通，「判定 → 生成 → 回填 → 改进」这条长链路全断**。

### 2.3 是否符合人类使用习惯

真实场景：工程师在 BOM 检查里发现「腕部法兰 A50，夹爪法兰 A40，装不上」。

| 真实动作 | 本板块支持 | 契合度 |
|---|---|---|
| 「发现装不上」 | ❌ 在另一个板块（bom-checker） | 断 |
| 「知道两侧是什么法兰」 | 需手动选 | ⚠️ 不能从判定结果带参 |
| 「生成转接板」 | ✅ | ✅ |
| 「确认这个板真的能用」 | ❌ 无几何校验、无实物反馈 | ❌ |
| 「装机后反馈」 | ✅ 有表单 | ✅ 好 |

> **关键 UX 缺口**：**「为什么需要转接件」的上下文没有传进来。** 用户要自己记住两侧法兰型号，再手动选。这与「一条龙」的人类习惯不符。

## 三、市场竞品与市场需求比较

### 3.1 竞品对照

| 竞品 | 定位 | 强项 | RoboParts 的差异 |
|---|---|---|---|
| **OpenSCAD / FreeCAD** | 开源参数化 CAD | 通用、可脚本化 | 通用工具，**不知道机器人法兰语义** |
| **CadQuery / build123d** | Python 参数化 CAD | 工程级、可进生产流程 | 同上，需自己写脚本 |
| **JellyCAD**（2025–2026） | 机器人专用可编程 CAD（Lua） | 面向机器人 | 需学 Lua；RoboParts 是「选一选就出图」 |
| **Zoo Text-to-CAD / AdamCAD**（2026 融资 410 万美元） | 自然语言 → STEP | 生成能力强、闭源 | 通用生成；RoboParts 是**领域专用 + 零门槛** |
| **earthtojake/text-to-cad**（8.3K star） | Agent 技能库，自然语言 → CAD | 生成 + 检查 + 导出 | 它是 Agent 侧工具；RoboParts 是 Web 侧零门槛工具 |
| **厂商转接板**（Robotiq 耦合件等） | 官方配件 | 认证可靠 | **只能买，不能生成**；RoboParts 可免费生成 |

> **生态位**：RoboParts 的独特价值是「**零门槛 + 领域语义 + 免费生成**」——用户不需要会 CAD、不需要装软件、不需要买官方件。**这个位置没有直接对手。**

### 3.2 市场需求实测

- 无独立需求信号（`demand-signal.json` 未细分）。
- 但**逻辑上需求明确**：跨品牌装配必然遇到法兰不匹配，而官方转接板往往「只配自家、要买、要等」。
- 关键阻碍：**没有一次真实的「生成 → 打印 → 安装 → 成功」案例**。这既是需求验证的缺失，也是信任建立的缺失。

> **判断**：需求**逻辑上成立**，但**零实证**。本板块最需要的不是新功能，是**第一个真实成功案例**。

## 四、最新开源技术融合评估

| 开源技术 | 2026 状态 | 接入点 | 融合形态 | 拒绝条件 |
|---|---|---|---|---|
| **OpenSCAD** | 已用（导出 .scad） | 导出层 | 保持 | — |
| **build123d / CadQuery** | 活跃 | 生成层 | 用 build123d 生成**参数化 STEP**（而非只出 STL/SCAD），可进真实生产流程 | 服务端引入 OCCT 体积大 ⇒ 可走前端 WASM 或按需 |
| **FreeCAD** | 开源 CAD | 导出层 | 提供 FreeCAD 工程文件导出 | — |

> **首选融合**：**build123d 生成参数化 STEP**。当前只出 STL（打印）与 SCAD（需装 OpenSCAD），**缺「可进生产流程的 STEP」**——这正是从「玩具」到「工程件」的分水岭。

2. **本板块的最大问题不是功能，是零实证**：没有任何一次真实「生成→打印→装机」记录。
3. `cad/` 与 `3d/` 占位符是**本轮实测新发现**，此前报告未提及。
4. 竞品信息为联网核实时点快照。
