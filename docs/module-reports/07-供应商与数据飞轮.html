一、板块定位与边界

一句话：让「供应商入驻 + 数据贡献」形成飞轮——外部提交的数据（BOM / 规格书）经机器核验后并入判定流。

两条子链路：

子链路 端点 实测状态
供应商生态 /api/suppliers/register（入驻）/ list（列表）/ inquiry（询价）/ quote（报价）/ approve（审核） ⚠️ 链路完整，无真实入驻
数据飞轮 /api/bom/import + /api/spec_declare + build_flywheel_layer.mjs ✅ 部分运转：entities.contrib.json 已含 142 条贡献实体

实测关键事实： - entities.contrib.json（2026-08-17 生成）142 条贡献实体，来自 OSS BOM（URDF 摄取）。 - 飞轮诚实纪律：URDF 不含机械接口事实 → mechanical_interface 一律留空（不编造）；用户 BOM 的机械声明必须过机械证据契约（source_url 必须是厂商官域 https 深链）。 - 20260915 修复留痕：「此前只判 if (!b.source_url)，于是 'Universal Robots' 这种公司名而非 URL 的字符串也能被采信」——这是极高质量的自我审计。 - suppliers_seed.json：仅 7 个品类组 / 6 个关键词组（种子数据）。

二、流程审计

2.1 流程是否合理

环节 是否合理 实测证据
贡献入库的诚实闸门 ✅ 极强 缺出处一律降级拒收；mech_evidence_contract.json 单一判据来源
贡献层不污染主库 ✅ 强 entities.contrib.json 与 entities.json 分离，运行时合并
规格书 → 结构提取 ✅ 合理 spec_declare.js 确定性正则，不调 LLM（后端挂了也能用）；AI 提取只能产 partial，绝不直接升 declared
供应商审核流 ✅ 合理 pending → approved / rejected，记录审核时间与原因
询价 → 报价 ✅ 合理 inquiry → quote 双向
供应商真实入驻 ❌ 零 KV 的 SUP 前缀无真实数据；suppliers_seed.json 只有 7 组种子
贡献者激励 ❌ 无 无署名、无积分奖励、无排行榜（credits 是消费积分，非贡献积分）
贡献量级 ⚠️ 偏小 142 条 vs 主库 868 条（约 16%）

判断：数据飞轮的「核验纪律」是世界级的（这是全仓最被低估的资产之一），但「参与动力」是零——没有入驻、没有激励、没有署名。

子链路 状态

结论：所有链路「逻辑上走通」，但除 OSS BOM 摄取外，全部零真实数据。

2.3 是否符合人类使用习惯

三类用户：供应商（想卖货）、贡献者（想贡献数据）、采购（想询价）。

用户 真实诉求 本板块支持 契合度
供应商 「我要接触买家」 需填 12 字段注册表 → 等审核 ⚠️ 门槛不低，且没有买家流量（鸡生蛋问题）
贡献者 「我贡献数据图什么？」 无署名、无激励 ❌ 没回答「图什么」
采购 「我要报价」 需 api_key + 积分 ⚠️ 摩擦

关键缺口：没有回答「贡献者图什么」和「供应商图什么」。 - 贡献者：项目在 CONTRIBUTING.md 说「加一条带出处的孔位数据比重构算法更有用」——但这是对项目的价值，不是对贡献者的价值。 - 供应商：项目明确「不抽佣金」（正确的中立性选择），但因此没有给供应商任何回报。

三、市场竞品与市场需求比较

3.1 竞品对照

竞品 定位 强项 RoboParts 的差异
阿里巴巴 1688 / 慧聪 B2B 采购 海量供应商 + 交易 有交易无技术判定
SourciumX / 全球 B2B 平台 跨境 B2B 撮合 通用工业品，无机器人语义
OpenBOM / PLMore BOM/PLM 供应链集成 无供应商入驻体系
OpenLoong / OpenLET（2026 国内） 开源社区 + 数据集 社区规模 2 万+ 开发者 它们有社区，RoboParts 有核验引擎——互补
Hugging Face datasets 数据集托管 分发 + 引用统计 无领域语义

生态位：RoboParts 的独特价值是「贡献数据经机器核验才入库」——这与「人多即可信」的众包模式根本不同。这是可写进论文的方法论（已在 contribution-loop-design.md 有设计）。

3.2 市场需求实测

  • 供应商：零入驻。
  • 贡献：entities.contrib.json 142 条（来自 OSS BOM 自动摄取，非人工贡献）。
  • 项目自述（README §12）：「最大的缺口是机械接口声明率……加一条带出处的孔位数据比重构算法更有用」——但没有人工贡献发生。

判断：供应商板块是「先建市场再找供需」的典型失败模式（没有买家流量，供应商不会来；没有供应商，采购不会来）。数据飞轮的核验能力很强，但缺「为什么要贡献」的答案。

四、最新开源技术融合评估

开源技术 2026 状态 接入点 融合形态 拒绝条件
OpenLoong / OpenLET 社区 2026 活跃（2 万+ 开发者） 贡献渠道 与国内开源社区互通贡献（他们缺核验，RoboParts 缺人） 需评估社区治理与许可
MinerU 开源文档解析 spec_declare 把「确定性正则」升级为「正则 + VLM 抽取」双通道（VLM 只产 partial） VLM 结果必须过 confidence 门控
证明携带贡献（Proof-Carrying Contribution） 2026 方法论 飞轮契约 贡献者提交 claim + evidence + verifier 三元组，质量由机器判定 不得用人数/声望判定质量
GitHub Sponsors / OpenCollective 已用 激励 把赞助与「贡献排行」挂钩 不得让赞助影响判定
W3C Verifiable Credentials 标准 贡献溯源 贡献者身份与贡献记录可验证 —
ROS Index / Awesome 列表 社区 供应商发现 从社区列表自动发现潜在供应商 —

首选融合：证明携带贡献（claim + evidence + verifier）。项目已有 mech_evidence_contract.json 与 build_flywheel_layer.mjs 的基础，只差把「贡献者提交核验脚本」这一层补上——这是「可验证的数据众包」，与项目方法论完全同源。

五、提升方案

P0（不做则板块不成立）

# 动作 验收判据
1 回答「贡献者图什么」：贡献者署名 + 贡献页（/contributors/<handle>）+ 公开贡献计数 至少 1 个真实外部贡献者留名
2 回答「供应商图什么」：明确「不抽佣」下的价值主张（如：免费获得兼容性判定背书 / 出现在 BOM 采购建议里） 供应商页面明确价值主张；至少 1 家真实入驻
3 贡献 → 判定改善的实证：记录「补了 N 条机械声明 → 可判定对增加 M」 ops/ 内有该前后对比记录

六、诚实边界

  1. 供应商生态零真实数据；本报告不把「有端点」等同于「有业务」。
  2. 数据飞轮部分运转：142 条贡献实体来自 OSS BOM 自动摄取，非人工贡献。
  3. 「不抽佣金」是正确的中立性选择，但同时移除了供应商的天然动力——这是需要正面回答的矛盾。
  4. 竞品信息为联网核实时点快照。
