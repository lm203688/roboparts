生成日期：2026-10-14 ｜ 板块编号：M5 ｜ 成熟度：C 档（能跑但未验证） 证据来源：functions/api/bom/check.js（385 行）、functions/api/bom/export.js（399 行）、functions/api/bom/import.js（90 行）、页面 bom-checker.html（243 行）、bom-manager.html（659 行）、bom-import.html（87 行）、order.html（14 行重定向）

一、板块定位与边界

一句话：从「一堆零件清单」到「能不能装、要多少钱、去哪买、怎么改」的全链路。

三个子功能：

子功能 页面 端点 做什么
兼容性检查 bom-checker.html /api/bom/check 两两兼容矩阵 + 可互换组 + 冲突告警 + 采购可购性标注
BOM 管理 bom-manager.html 前端 localStorage 本地 BOM 增删改 + 导出 CSV/JSON
BOM 导入（飞轮入口） bom-import.html /api/bom/import 用户提交 BOM → 结构校验 → 待审队列（bom:pending:*）
导出 — /api/bom/export CSV / JSON，含供应商建议与总成本

实测关键参数： - bom/check：免费层 ≤ 12 个组件，Pro 无限制；三源目录加载（data.json / oss_components.json / entities.json），全失败返回 503（不静默降级）。 - bom/export：每次消耗 1 积分。 - bom/import：机械接口声明必须附 source_url 才采信，否则拒绝该条；写入待审队列，不直接进裁决流。

二、流程审计

2.1 流程是否合理

环节 是否合理 实测证据
BOM → 两两判定 ✅ 合理 复用 compat_engine 的 evalDimension，不自带副本（曾自带副本已删，注释留痕）
目录加载失败处理 ✅ 强 「全失败 → 503；部分失败 → 显式标注目录降级」——避免「我们没读到库」被渲染成「这些零件没数据」（假证据不足）
降级标记按请求创建 ✅ 强 注释明确「模块级可变状态会跨请求累积」（同 mcp.js 模块顶层 Math.random() 事故）
导出计费 ⚠️ 合理但摩擦 1 积分/次
导入的诚实闸门 ✅ 强 「不可核实的接口事实 = 污染」；机械声明必须附 source_url
导入不直接进裁决流 ✅ 强 走待审队列，避免任意提交污染线上结论
自检流量隔离 ✅ 强 x-roboparts-selftest 只预览不落盘
BOM 存储 ⚠️ 弱 bom-manager 用 localStorage（本地），换设备即丢失；无账户级持久化
BOM → 采购 ⚠️ 半通 check 有采购可购性标注，但无「一键下单」真实链路（order.html 仅 14 行重定向）

判断：判定与导入环节的纪律极强（防假绿、防污染、防降级误读），但存储与交易环节弱。

2.2 是否全面走通

子链路 状态
输入 BOM（手填/粘贴）→ 检查 → 矩阵 ✅ 通
检查 → 可互换组 / 冲突告警 ✅ 通
检查 → 采购可购性标注 ✅ 通（getPurchaseOptions）
本地管理 → 导出 CSV/JSON ✅ 通（需 key + 积分）
导入 → 待审 → 飞轮合入 ⚠️ 链路完整但无真实贡献数据
BOM → 转接件生成 ❌ 断
BOM → 下单 ❌ 断（order.html 只是重定向）
BOM → 账户级持久化 ❌ 无
真实用户使用 ❌ 无证据

结论：检查链路完整，但「存、改、买、改件」四步全断或弱。

2.3 是否符合人类使用习惯

真实采购/工程师的 BOM 工作流：Excel 里维护清单 → 查兼容 → 改清单 → 询价 → 下单 → 收货。

真实动作 本板块支持 契合度
「我在 Excel 里有清单」 支持粘贴/导入 ⚠️ 需确认 Excel 直读能力
「我常改这个清单」 localStorage 本地存 ⚠️ 换设备丢
「给同事看」 无分享链接 ❌
「询价」 供应商板块有 inquiry，但未从 BOM 串起 ❌ 断
「下单」 order.html 空 ❌

关键 UX 缺口：BOM 是「一次性工具」而非「持续资产」。用户每次来都要重新粘贴。人类习惯是「我的 BOM 一直在那儿」。

三、市场竞品与市场需求比较

3.1 竞品对照

竞品 定位 强项 RoboParts 的差异
OpenBOM 云 BOM/PLM 多 CAD 集成、版本管理、ERP 对接 通用制造业；不做兼容判定
PLMore 开源 PLM 开源、现代 通用 PLM；无机器人语义
KiCad BOM 电子 BOM 导出 与 EDA 深度集成 电子域；无机械兼容
厂商 BOM 工具 单厂配套 准确 不跨品牌
Excel / Google Sheets 通用表格 人人会用 无兼容判定——这正是 RoboParts 的价值点

生态位：RoboParts 的独特价值是「BOM + 跨品牌兼容判定」的组合。OpenBOM 管 BOM 不判兼容，Excel 判不了兼容。这个组合目前无对手。

3.2 市场需求实测

  • 无独立需求信号。
  • 但 bom/check 的 FREE_ITEM_LIMIT = 12 暗示设计者认为「免费用户会来试」——但没有使用量证据。
  • bom/import 作为「数据飞轮入口」被定位为 P0，但没有任何真实提交。

判断：BOM 检查是最容易被理解和传播的功能（「粘贴清单，告诉你哪里装不上」），但转化路径被计费和存储摩擦挡住。

四、最新开源技术融合评估

开源技术 2026 状态 接入点 融合形态 拒绝条件
OpenBOM API 商业（有 API） 导出层 借鉴其「BOM 版本 + 多 CAD 集成」；不自建 ERP 商业依赖需评估
PLMore 开源 PLM BOM 存储 借鉴其数据模型做账户级 BOM 持久化 不宜整仓引入
KiCad / IPC-2581 / STEP AP242 标准 导出层 支持标准 BOM 交换格式（含 STEP AP242 BOM） —
Cloudflare KV / D1 已用 KV 存储层 把 BOM 从 localStorage 迁到 KV/D1（账户级持久化） 需设计隐私（对齐「端到端加密」目标 5）
spreadsheet 解析（SheetJS） 开源 导入层 支持 Excel/xlsx 直接导入 —
Workflow-as-tool（MCP） 2026 趋势 已有端点 把「BOM 检查 + 拓扑排序 + 缺口报告」暴露为一个工具 不得另写判定逻辑

首选融合：BOM 账户级持久化（KV/D1）+ Excel 直读。当前 localStorage 是最弱的一环，而人类习惯是「BOM 一直在那儿」。

五、提升方案
