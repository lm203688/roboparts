0执行摘要：一句话结论

核心判断

RoboParts 的技术与研究完成度远高于其产品与商业完成度。 数据层、判定引擎、溯源层、工程纪律已达到「可发表、可复现、可审计」的水准（研究侧完成度自评 63.2%，本报告认为在本域口径下甚至更接近上限）； 但对外产品仍停在「零件库 + 兼容性查询」的旧叙事，商业侧从 0 到现在仍是 0（0 star / 29 次调用 / 0 注册）。 这不是能力问题，是价值主张与市场时机没有对齐的问题。

三条战略判断

判断 1

完成度指标本身需要「分层」，而非继续调口径

项目已把「不该算缺口的移出分母」做了五轮修正。继续调口径边际收益已尽。 正确做法是把单一分数拆成三个独立分层的完成度：数据/研究层、产品层、生态/商业层——三者不应用同一个数字概括。

判断 2

最大机会在「国标接口标准」这一时间窗

中国《人形机器人与具身智能标准体系(2026版)》已发布，一体化关节接口国标、《人形机器人模块化通用技术要求》正在起草。 行业实测痛点正是「厂商技术文档关键参数缺失」——与 RoboParts 的三态诚实数据层精准咬合。

判断 3

产品必须从「零件库」升级为「集成决策器」

用户真实问题不是「有哪些零件」，而是「我这台机器人能不能同时装夹爪 A 和传感器 B」。 co_mount 层已具备回答能力，却未做成面向用户/Agent 的查询入口。这是当前 ROI 最高的产品化动作。

1.2 技术架构

运行时

静态 HTML 页面 + Cloudflare Pages/Workers Functions（functions/）后端。_middleware.js 承担鉴权/限流，functions/api/* 提供 REST，functions/mcp.js 暴露 MCP Streamable HTTP。

数据管线

唯一真相源 api/entities.json，全部对外数字由 scripts/*.py 现算注入，禁止手改。regen_derived.py 重生成派生文件，inject_readme_stats.py 注入 README。

Agent 分发

机器可读四件套（server.json / smithery.yaml / lhm.plugin.json / .well-known/mcp.json）+ A2A v1.0 Agent Card（.well-known/agent-card.json）。

1.3 工程质量（这是项目最强的一块）

  • 多层闸门：ci_gate.py 顶层 38 项（含 schema 契约、mount_type 枚举、分发一致性、无凭据泄漏、拓扑排序等），2026-10-05 记录合计 84 项检查全绿。
  • 反向注入（mutation tests）：verify_l*_injections 系列对每条判据做「阳性 + 阴性 + 变异」三对照，历史栽过 3 次「假绿」，是最领先的实践。
  • 单一真相源 + 现算：所有对外数字走 onboarding_block.facts()，禁止手写副本。
  • fail-closed：不可判定判「未知」而非「通过」；not_declared 显式登记为缺口而非字段缺失。
  • 纪律留痕：.workbuddy/memory/ 逐日工作日志 + MEMORY.md 长期约定，记录了 20+ 条可复用判据纪律。
⚠️ 扫描中发现的两处「自己违反自己纪律」的漂移（可立即修）
  • README 顶部统计块过期：README 写「802 实体 / 机械声明率 5.69%（25/439）」，而 entities.json 现算为 868 实体 / 16.2%（81/500）。该块由 inject_readme_stats.py 生成，说明数据增长后未重跑注入。
  • count 字段过期：entities.json 的 count=865，而 entities[] 实际长度与 category_counts 合计均为 868（差 3）。

讽刺点：一个以「单一真相源、禁止手改数字」为核心价值的项目，最高曝光位（README 第一屏）反而漂移了。建议把「README 统计块 + count 字段」纳入现算巡检。

「不是「还没做完」，是三类性质完全不同的缺口混在一个分数里」—— ① 真缺口（可工程推进，如确定性裁决率 0.1%）；② 锚点排除（补了即违规，如连接组/拓扑数据）； ③ 物理上限（补不了，如闭源模型无公开验证栈）。结论是：在「本域应做事项」口径下当前已接近上限。

2.2 本报告的独立判断：分数应分三层看

63.2% 是一个「本域研究口径」的数字，它把「我们应做且能做的事」做得很扎实。但它不能代表项目整体健康度——因为核心目标的另一半（生态化、可被真实用户/Agent 使用）几乎未被这个分数度量。建议改为三层分别判断：

层级度量什么本报告评估判据
L1 数据 / 研究层 判定能力、溯源诚实度、关系类型、工程纪律 ~63% 且近本域上限 项目自评 + 本报告核对（闸门全绿、口径自洽、诚实边界完备）
L2 产品层 用户能否用它解决真实问题 ~30% 定位分裂 6 套；核心能力（共装判定）未产品化；README 数字漂移

✅ 对完成度判据本身的两点肯定

① 判据可复现、现算、带反向对照（co_mount 归零 ⇒ 完成度必须回落），这是业内罕见的方法论严谨； ② 主动纠正了「判据惩罚正确行为」（neuron 维从「造数据量」改为「溯源诚实度」）——这比数字本身更有价值。

⚠️ 对完成度判据的两点建议

① 停止继续调口径：五轮「移出分母」已到边际收益递减点，继续会让指标越来越像「自我安慰」。 ② 新增「L2/L3 完成度」指标：至少加入「核心能力产品化率」「外部交互痕迹数」「被引用/被调用数」三项，否则指标永远测不出真正的短板。

3板块级诊断与提升建议

按 12 个板块逐项给出：现状 → 问题 → 提升建议（含优先级）。优先级：P0 立即 · P1 短期 · P2 中期。

A · 数据层（实体库）

现状：868 实体 / 20 品类，执行器 222、平台 106、芯片 108、传感器 95；机械声明率已从 5.69% 提升到 16.2%（81/500）；国产替代索引 import_substitution_for + 供应链 supply_chain 字段已建。

问题：① 机械声明率提升主要靠「补厂商 datasheet」，但已证「单条声明边际收益为 0」（T2 定理），补数据的 ROI 需按同质集批量衡量；② 数据总量仍偏小（对比 TraceParts 千万级），且跨厂商可比 A 级条目为 0；③ 品类深度不均——连接器/线缆/PCB/电源各仅 2 条。

提升建议
  • P0 数据口径自动化巡检扩容：把 README 统计块、count 字段、各页 data-rp 锚点纳入 verify_live_numbers.py 的四轴巡检，消除「自己违反自己纪律」的漂移。
  • P1 按同质集（MVC）批量取证，而非逐条补：优先补齐 16 个 L2 节点的 electrical 声明（现 9/16），让 co_mount 假说升格为定理。
  • P1 接入国标信息模型：对齐正在审查的《机器人 服务机器人模块化 第201部分：模块通用信息模型》(20255807-T-604)，让实体 schema 成为国标的开源落地实现（见 §5）。
  • P2 品类补深：连接器/线缆/电源补齐到可用规模（各 ≥15 条），否则「四维兼容」的电气维永远无米下锅。

B · 判定引擎层（两套引擎的断层）

现状：项目同时存在两套引擎——产品面 compat_engine.js（protocol/electrical/mechanical/software 四维）与研究层 compose_engine.py（mechanical/electrical/signal 三轴）。维度交集只有 2 个，不互为子集。

问题：研究层靠类型级裁决做更细判定（signal 覆盖 60.1%），产品层却靠 4–6% 的字段覆盖对外回答——更准的一套没人看得到。已用 4 个桥接 MCP 工具缓解（0/5 → 5/5 可达），但两套口径同时对 Agent 可见仍有混淆风险。

提升建议
  • P0 观察桥接调用量后收敛到单一真相源：若 explain_* 系列调用量低，说明 Agent 仍在用旧四维；应评估 OPT-1（产品面换真相源）。
  • P1 定义「维度映射表」：明确 protocol/software（产品层）与 signal（研究层）的关系，把两套维度统一到一份可声明的映射契约，避免长期双轨。
  • P1 把「确定性裁决率」做成对外可查指标：当前 114/214840 是诚实画像，但对外应配一句「为什么低」的归因（关系类型错配 + 证据缺口），而非只给数字。

C · 关系类型层（组合的语义）

现状：已有 peer-to-peer（二段互插）+ co_mount（三段 A↔宿主↔B）两类关系，共装可判定率 82.5%（297/360），新增 port_exhausted 裁决态（装不下 ≠ 不知道）。

问题：composed（点对点正向兼容）仍为 0；跨本体/转接链路/多工具挂载未建模；宿主库只有 3 个本体。

提升建议
  • P0 把 co_mount 做成用户可查产品（见 D 板块）：这是当前唯一能直接回答「真实用户问题」的关系类型。
  • P1 扩宿主库：从 3 个本体扩到 15–20 个（覆盖 UR / Franka / 主流协作臂 + 若干人形），共装判定可线性提升。
  • P2 第三类关系「链路级可装性」：多个零件能否组成一条可用链（整机级可装性图），是 D5 范畴论路线的自然延伸。

D · 溯源层（链路可溯源）

现状：PROV-O 契约已建，Tier A 可点开复核 469 条（54.2%），本域三段链 2/2 闭合；跨域全链 0/1（断点在 body，属外域）。

问题：溯源只覆盖到「零件 → 厂商 datasheet」，尚未覆盖「零件 → 实体 → 关系 → 判定结论」的判定过程溯源；Agent 调用后无法回溯「这条判定依据了哪几条声明」。

提升建议
  • P0 判定结论带「证据链」返回：每个兼容判定结果附 evidence[]（引用了哪几条实体声明 + 各自 tier），让 Agent 可复核、可转述。这是「链路可溯源」从数据层延伸到判定层的关键一步。
  • P1 对齐 Croissant 1.1 / W3C PROV-O：生态已就绪（700K 数据集在用），RoboParts 的溯源层可直接复用，提升学术引用与合规叙事。
  • P2 EU AI Act 可追溯性叙事：把「可溯源」对接合规刚需，是面向企业客户的差异化卖点。

E · 标准对齐层（这是被低估的最大机会）

现状：核心目标明列「对接《人形机器人模块化通用技术要求》国标」，已有 ISO 9409-1 法兰判定与 standard-audit 页。

问题：国标侧动作尚未系统性接入——目前只对齐 ISO，未对齐 2026 新发布的国标体系。

🎯 巨大机会窗口（详见 §5）

中国已发布《人形机器人与具身智能标准体系(2026版)》（六大板块），且一批关键标准正在制定/征求意见：《人形机器人模块化通用技术要求》(20262893-T-604)、一体化关节接口标准（北京人形牵头，即将征求意见）、服务机器人模块化·模块通用信息模型 (20255807-T-604)。 这些标准的「模块信息模型」与 RoboParts 的实体 schema 是同一件事——RoboParts 有资格成为这些标准的开源参考实现。

提升建议
  • P0 建立「国标映射层」：把 GB/T 43200-2023（一体化关节性能）、GB/T 43210.1-2023（服务机器人模块化·通用要求）、GB/T 38560-2020（通用驱动模块接口）映射到实体字段，新增 standard_conformance 的 GB 维度。
  • P1 跟踪并预对齐在制标准：一体化关节接口国标（即将征求意见）+ 模块通用信息模型（审查中），第一时间把 schema 对齐，抢占「标准开源实现」位置。
  • P1 参与标准共建：以「开源数据层」身份向标委会提交接口数据格式建议，学术+标准双背书。

F · 产品 / 前端层

现状：38 个 HTML 页，覆盖选型、BOM 检查、设计画布、URDF 库、转接件生成、Copilot 等。

问题：① 定位分裂（历史诊断发现 6 套口径，已部分整改，仍需巡检）；② 核心能力（共装判定）没有产品入口；③ 首页 H1「机器人零件能不能装到一起？」很好，但下一句没接住「共装」这个真实场景。

提升建议
  • P0 新增「能不能共装」查询页：输入宿主机器人 + 器件 A + 器件 B → 返回 mountable / port_exhausted / type_error / unknown（带证据链）。把价值主张从「零件库」升级为「集成决策器」。
  • P0 修复首页数字漂移：统一走 facts()，消除 README 802/868 与 5.69%/16.2% 的矛盾。
  • P1 页面收敛：38 页里有若干「过程产物页」（promotion/promo-poster/demo-flow 等），建议按受众重组为「构建者主线（选型→BOM→共装→转接件）」+「Agent 入口」两条路径。
  • P1 移动端与可访问性：抽查响应式与对比度，提升国际用户可用性。

G · API / 开发者层

现状：REST API + 免费 key（30 秒领取，100 次/小时，无需信用卡）+ OpenAPI 规范；隐私上邮箱仅存 SHA-256。

问题：免费额度与限流口径在 research_progress.json 里出现不一致（free_credits:100 与 rate_limit_per_hour:30 并列），易让开发者困惑。

提升建议
  • P0 统一额度口径：明确「免费额度 / 限流」是同一量还是两个量，对外文档只保留一个可核验数字。
  • P1 补齐 OpenAPI + SDK 示例：Python / TypeScript 各一份 20 行示例；提供 curl 一键复核（已在 access 字段有基础）。
  • P1 判定结果 schema 化：定义 CompatibilityVerdict 契约（含 evidence/caliber/unknown 原因），让下游可程序化消费。

H · MCP / Agent 生态层

现状：20 个 MCP 工具（业务 + 桥接）、stdio + hosted 双形态、4 家分发全绿、A2A v1.0 Agent Card 已落地。生态位地图已建（6 层）。

问题：① A2A SendMessage 桥接端点未上线（Card 声明了但端点未实现）；② L4 编排层（LangChain/CrewAI/n8n）无接入示例；③ L5 Golden 评估集未落地。

提升建议

4.3 RoboParts 的差异化位置（三态诚实 × 中立 × 组合判定）

护城河 1

三态诚实判定

唯一公开登记「答不出来」的数据层。当行业实测痛点就是「厂商文档缺参数」时，敢说「不知道」反而成为最可信的卖点。

护城河 2

中立第三方裁决

不生产、不销售、不代理任何零件——「卖家不适合同时当裁判」。厂商自建选型器结构性无法复制。

护城河 3

组合/共装判定

不止「A 能不能插 B」，还答「A 和 B 能不能同时装在同一台机器人上」——co_mount 关系类型是全网独有。

⚠️ 竞品威胁提示

roboxdb.com 的出现说明「source-backed 机器人零件数据」这一象限已有人进入。RoboParts 的窗口期在于：把「判定引擎 + 共装查询 + 国标对齐」做成它没有的能力，而非在「零件数量」上与其竞争。

8一页结论

RoboParts 已经在「研究」这条路上走到了本域上限附近——它有可复现的定理、可审计的闸门、可追溯的数据，以及一个诚实的完成度指标。它缺的不是更多数据，而是把这份能力翻译成市场能感知的价值。

三件事决定它能否从「优秀的开源研究项目」变成「有人真的需要的基础设施」：

  1. 产品化核心能力——把 co_mount「能不能共装」做成查询，让价值主张从「零件库」变成「集成决策器」；
  2. 抓住国标时间窗——对齐正在制定的「一体化关节接口」「模块通用信息模型」国标，成为标准的开源参考实现；
  3. 停止调口径，开始测市场——完成度指标已足够诚实，接下来要用「被调用 / 被引用 / 被付费」来度量。

一句话检验法仍然成立：「这件事是在让组合变得可校验，还是在让列表变得更好看？」——本报告的每一条建议，都应通过这个检验。
