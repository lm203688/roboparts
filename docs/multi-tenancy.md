# 多租户边界（Multi-Tenancy Boundary）

> **Phase 3 承重结构 5**（审计 §4 "多租户"）。
>
> RoboParts 目前是**单租户**：所有数据公开，注册后共用一个 API Key
> 池。本文件不是要立刻改多租户，而是**先诚实登记边界**——避免"看着像
> 能做多租户"的假承诺。真正的多租户改造属于 3-6 个月的独立工程。

## 一、当前模型（v1 · 单租户公开池）

```
用户 → 申请 API Key → USER_CREDITS KV（key=user_id → {quota, history}）
                    → 请求打 API_KEYS KV 查 apiKey → 全局实体库
```

**关键特征**：
- 数据面：所有实体对所有人可见（CC BY 4.0）
- 配额面：按 apiKey 计次，配额上限由 env 全局配置
- 隔离面：**没有**——A 用户无法看到自己的私有数据，也无法阻止 B 用户看到
  与 A 相同的公开实体

## 二、边界契约（不可含糊的三态）

对外的所有"多租户"暗示必须诚实标注：

| 声明 | 现实 | 对外口径 |
|---|---|---|
| "支持多用户" | ✓ 每人独立 apiKey | 保留 |
| "数据隔离" | ✗ 无隔离 | 必须不写 |
| "支持私有声明" | △ 走 supplier-admin 后台，未鉴权即全局可见 | 改为"提交后进入审核队列" |
| "SLA 按用户保证" | ✗ 共享 Cloudflare Workers | 必须不写 |

**硬规矩**：任何新增页面/文档出现"多租户""数据隔离""专属存储"
必须走本文件的**审批清单**（下方）。

## 三、真正的多租户需要什么（诚实的成本估算）

如果 T2 集成商客户提出真正的多租户需求，需要：

| 层 | 改动 | 估算 |
|---|---|---|
| 存储 | 引入 Postgres + RLS，按 tenant_id 分片 | 3-4 周 |
| 鉴权 | 从 apiKey 升级到 JWT + tenant claim | 1-2 周 |
| 数据面 | 现有 42 个 `functions/api/*` 加 tenant filter | 4-6 周 |
| 计费面 | Stripe/Creem 按 tenant 分账 | 1-2 周 |
| 合规面 | 数据导出/删除 SLA | 1-2 周 |
| 测试 | 隔离测试 + 权限矩阵测试 | 2-3 周 |
| **总计** | | **12-20 周（3-5 个月）** |

## 四、审批清单（改动前必过）

任何涉及租户/隔离/私有的改动：

- [ ] 是否会让当前单租户模型出现"部分承诺、部分实现"的模糊态？
- [ ] 是否已在本文件登记该改动的位置和口径？
- [ ] 是否已同步更新 `api/schema_migrations.json`（若涉及数据结构）？
- [ ] 是否已同步更新对外页面（避免 marketing 侧先跑）？

## 五、当前已知的相关承诺（诚实登记）

- `supplier-admin.html`：供应商后台提交声明，走人工审核后入全局库
  ——**不是**"私有声明"，落地后全局可见。对外口径需明确。
- `supplier-admin.html`：登录方式（当前无鉴权，走 IP 白名单）——Phase 3
  待办：加 API Key 鉴权。
- 注册后 API Key：按用户配额，但数据面共享——对外**不**承诺"数据隔离"。
