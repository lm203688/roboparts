# RoboParts 地基审计与硬骨头攻坚报告

> **生成日期**：2026-10-16
> **审计范围**：全仓静态扫描 + 代码级原文阅读 + 产物现算 + 依赖链核对 + **线上回探**
> **审计方法**：不看文档声称什么，只看**实测证据**。凡与文档不一致处，以实测为准并显式标注。
> **报告性质**：地基体检 + 攻坚方案。**不构成合规声明**。所有数字可复现（给命令 / 给路径）。
> **一句话立场**：这份报告专挑地基。**避开"又加了什么能力"，只谈"已经盖起来的楼站不站得住"。**

---

## 0. 结论先行

**楼盖得很快。** 一周之内 Phase A/B/C 跑完，CI 闸门 49 → 60，`compose_core.py` 抽出来了，证据账本建了，ISO 22166 映射表建了。速度是真的。

**但地基有六处裂缝，其中一处正在线上发生。**

| # | 地基裂缝 | 风险 | 是否线上可见 |
|---|---|---|---|
| **F1** | **公开宣传的数据集端点 `/api/data.json` 是 767 条旧数据，而站点到处写"868 条"** | 🔴 **极高**（公开可信度） | ✅ **正在发生** |
| **F2** | 单一真相源自身不自洽：`entities.json` 有 **3 个不同的 updated**；仓内 **3 份实体副本**结构互不相同 | 🔴 极高 | ⚠️ 间接 |
| **F3** | 最强验证（`regression.py` 11,430 行）**只在本地跑**，且依赖被 gitignore 的 `ops/` ⇒ 外部不可复现 | 🔴 极高 | ❌ 但决定 PR 可信度 |
| **F4** | **无测试框架、无覆盖率、无 `npm test`**；测试:代码 ≈ **1:111**；5 个测试里 2 个从未接入任何自动链路 | 🟠 高 | ❌ |
| **F5** | 契约层薄弱：80 个产物只有 **2 个 schema**；`confidence` 是无约束浮点（26 种取值）；**61 条实体（7%）无 `source`**，违反"无出处不收"铁律 | 🟠 高 | ⚠️ 间接 |
| **F6** | 安全与恢复：CSP 含 `unsafe-eval`、`/api/*` 全开 CORS、限流只是响应头、**无备份**、`mcp-server/` 已发布但被 gitignore | 🟠 高 | ✅ 部分 |

**核心判断**：**F1 + F2 是同一条病——"单一真相源"在地基层面没有强制执行机制。** 项目花了巨大精力在**引擎层**做 fail-closed、三态守恒、阴阳自证，但**产物层和分发层是 fail-open 的**：谁都可以写一份 `api/*.json`，没人知道它过期了，也没有闸门拦它。**引擎越精密，喂给它的数据过期就越危险——因为精密引擎会把过期数据算出一个看起来可信的错答案。**

## 2. 六层地基体检

### 2.1 数据地基：单一真相源是**声明**，不是**机制**

**实测证据：**

| 证据 | 实测值 |
|---|---|
| `entities.json` 三个 updated | top-level `updated` = **2026-09-25** / `last_updated` = **2026-10-06** / `meta.updated` = **2026-10-15** |
| 实体副本 ① | `api/entities.json` — 868 条，扁平 `entities[]` |
| 实体副本 ② | `api/data.json` — **767 条**，扁平 `data[]`，`generated_at` = **2026-08-27** |
| 实体副本 ③ | `data.js`（git 跟踪，1.7MB）— `const DB = {...}`，**按品类分键**（actuators/sensors/...），结构与前两者都不同 |
| 线上回探 | `https://roboparts.cc/api/data.json` → `entity_count=767`，`generated_at=2026-08-27T14:54:22Z`，**而同一文件里 `total_entities` 写 868** |
| 过期产物 | **16 / 80** 个 `api/*.json` 的 `generated_at` 早于 2026-10-01；最老的 `cross-refs.json` 停在 **2026-06-18**（4 个月前） |
| 生产者数量 | **108 个脚本**向 `api/` 写入；真相源 `facts()` 只有 **1 处**（`scripts/onboarding_block.py`） |

**为什么这是地基问题（不是数据问题）：**

1. **`entities.json` 对自己都不一致**——三个时间戳互不相等。一个连"我什么时候更新的"都答不一致的文件，被当作全站唯一真相源。
2. **三份副本没有一致性闸门**。`data.js` 和 `data.json` 与 `entities.json` 是**不同结构**，任何"逐字段对账"的闸门都无从下手——因为对不上不是 bug，是结构不同。
3. **公开外链指向旧数据。** `404.html`、`api-pricing.html`、以及**每一篇文章的页脚**都写着"868 个实体 / 下载结构化数据"并链到 `/api/data.json`——而它返回 767 条、生成于 8 月 27 日。**这是对外可见的、可被任何人一次 curl 戳破的自相矛盾。**
4. **没有产物依赖图。** 108 个脚本写 `api/`，但"谁依赖谁、改了 A 该重跑谁、谁过期了"**无人知道**。这是典型的"能跑，但不可控"。

**这一条的严重性被引擎的精密放大了**：`compose_semantics.json` 用 430,336 对算出 `composed=0`，并给出精确归因。但如果**输入实体是过期/错配的**，这套精密推导会输出一个**看起来很可信的错答案**——而项目引以为傲的 49→60 道闸门里，**没有一道管单产物新鲜度**。

### 2.2 验证地基：重，但不可组合、不可复现

**实测证据：**

| 证据 | 实测值 |
|---|---|
| `scripts/regression.py` | **11,430 行**（单体） |
| `scripts/ci_gate.py` | **3,044 行**（单体） |
| 测试框架 | **无**（无 pytest / vitest / jest / node:test 依赖） |
| 覆盖率测量 | **无** |
| `npm test` | **不存在**（`package.json` 无 `test` 脚本；`tests/README.md` 自己写了"或在 package.json 里加一条"，**但从未加**） |
| 测试:代码 | **759 : 84,185 ≈ 1 : 111** |
| `functions/` | 55 个源文件 / **1 个**测试文件 |
| CI 实际跑什么 | **只有 `ci_gate.py`**；`regression.py` 不在 CI 里 |
| `ops/` | **在 `.gitignore` 中**（`.gitignore:56`）⇒ 依赖 `ops/` 的回归断言**外部人无法复现** |
| `tests/` 5 个测试 | CI 只调 **3 个**（bom_assembly / feedback_loop / promote_ledger）；`test_p0_multifactor.mjs`、`test_p1_recommender.mjs` **从未接入任何自动链路** |
| 变异评分 | 6 个变异体、kill 1.00，但自述"**作用点在产物层**，不直接证明引擎层" |

**为什么这是地基问题：**

- **验证的"强度"和"可复现性"是两件事。** `regression.py` 有上千条断言，很强；但它 (a) 是 11,430 行单体，(b) 不在 CI，(c) 依赖一个被忽略的目录。⇒ **一个外部 PR 贡献者无法在本地复现你的最强验证**，那他怎么知道自己的改动没破坏东西？答案是他不知道。**这直接把"开源协作"这条路堵死了**——而项目的核心目标之一就是生态。
- **没有测试框架 = 没有"测试"这个一等公民。** 断言散落在生成脚本、闸门脚本、`verify_*` 脚本里，跑绿了也不知道绿在哪（`tests/README.md` 自己都写了这条约束）。
- **1:111 的比例意味着：任何重构都是盲改。** 上一份报告建议"消除重复实现"（43 个文件含兼容判定逻辑）——**在没有测试的情况下做这件事，等于在雷区里蒙眼走。** 这就是为什么那条 P0 一直标着"本轮不做"。**地基不牢，导致上层该做的事做不了。**

### 2.3 契约地基：80 个产物，2 个 schema

**实测证据：**

| 证据 | 实测值 |
|---|---|
| `schemas/` | 只有 **2 个**：`embodiment_provenance.schema.json`、`evidence_contribution.schema.json` |
| `api/*.json` | **80 个**产物；`entities.json` **自己没有 schema** |
| `confidence` | **无约束浮点**，26 种取值（0.3 ~ 1.0），**无语义分层、无枚举、无文档** |
| `source` 缺失 | **61 条实体（7.0%）** |
| `source_url` 覆盖 | **581 / 868 = 66.9%** |
| 版本化契约 | 无 API 版本头 / 无弃用策略 / 无变更日志契约 |

**为什么这是地基问题：**

- **`confidence` 是这套系统里最该被信任的字段，却最没有定义。** 0.55 和 0.58 差在哪？谁定的？跨实体可比吗？**没有人能回答**——因为它是自由文本式的浮点。当 Agent 拿它做决策时，它提供的不是置信度，是**装饰**。
- **"无出处不收"是项目的第一铁律，但 61 条实体没有 `source`。** 铁律写在 `README.md` §12 和 `CONTRIBUTING.md` 里，**但没有闸门管存量数据**。⇒ 铁律只约束新增，不约束存量 ⇒ 存量在无声腐化。
- **80 个产物只有 2 个 schema** ⇒ 产物的结构靠生成脚本的"当前实现"隐式定义。任何一个脚本被改，下游消费者**无契约可依**。

### 2.4 运行时与安全地基

**实测证据（`_headers` / `wrangler.toml`）：**

| 项 | 实测 | 问题 |
|---|---|---|
| CSP | `default-src 'self' 'unsafe-inline' 'unsafe-eval' ...` | **`unsafe-inline` + `unsafe-eval` 同时存在**，而仓内有 41 个页面、`designer.html` 单页 2,187 行内联 JS ⇒ **CSP 的 XSS 防护基本失效** |
| CORS | `/api/*` → `Access-Control-Allow-Origin: *` | 任意站点可跨域消费 API（同时又有积分/付费墙，语义冲突） |
| 限流 | `X-RateLimit-Limit: 60` 只是**响应头声明** | 响应头不执行限流；真实限流是否生效**无验证** |
| HSTS | **缺失** | 无 `Strict-Transport-Security` |
| 运行时版本 | `compatibility_date = "2024-09-23"` | 距今 **2 年+**，运行时行为漂移 |
| KV 绑定 | 5 个（USER_CREDITS / API_KEYS / SUPPLIERS / SUPPLIER_INQUIRIES / URDF_LIBRARY） | **无备份 / 无恢复脚本** |
| 依赖锁定 | 根目录**无 `package-lock.json`**；`requirements-dev.txt` **只有 PyYAML** | 依赖未锁版本，供应链不可复现 |

**一处值得表扬**：`functions/api/bom/check.js` 的 KV 降级处理是**正确**的——`degraded` 收集器**按请求创建**（不是模块级数组），且显式透传，避免"供应商库没读到"被渲染成"没有供应商"。这是地基该有的样子。**问题是：这种纪律是点状的，不是体系化的。**

### 2.5 架构地基：耦合与"孤岛"

**实测证据：**

| 证据 | 实测值 |
|---|---|
| 首页链出 | **19 / 41** 个根页面；**20 个未链出**（含 `parts-viewer` / `compatibility-viewer` / `standard-audit` / `suppliers` / `spec-declare` / `credits`） |
| 兼容判定逻辑散落 | **43 个文件**含 `compatible/incompatible` 判定 |
| 内联 JS 规模 | `designer.html` **2,187 行**、`assembly.html` 619、`data-hub.html` 491、`bom-manager.html` 444、`adapter-generator.html` 382、`selection.html` 365 |
| `mcp-server/` | **在 `.gitignore` 里**，但它是**已发布到 npm 的包** |
| `data.js` | git 跟踪的第三份真相源 |

**为什么这是地基问题：**

- **`designer.html` 2,187 行内联 JS** 意味着：一个 123KB 的 HTML 文件里塞着一套完整应用逻辑，**没有模块边界、没有测试、没有类型、无法被复用**。任何对它的改动都是"改一处、炸一片"的高风险操作。**这不是"设计画布"的问题，是"没有前端架构"的问题。**
- **`mcp-server/` 被 gitignore 但已发布** ⇒ **发布的代码不在版本控制里**。npm 上的包和仓库里的包可能不一致，且**无法追溯哪个 commit 对应哪个 npm 版本**。这是典型的 split-brain。
- **20 个页面未链出**：`standard-audit`（标准合规）、`spec-declare`（声明通道）、`suppliers`（供应商）——**这些是核心功能页，但用户从首页走不到。** 上一份报告说"五个孤岛"，**实测是二十个孤岛。**

**实测证据：**

| 证据 | 实测值 |
|---|---|
| 部署暂存 | `.deploy-staging` = **148MB / 5,341 文件** |
| 其中大文件 | `api/training_dataset.json` **19MB**、`api/step_parts.json` **5MB** |
| 平台上限 | Cloudflare Pages：单文件 25MB / 总文件 20,000 |
| 新鲜度 | `.deploy-staging` 时间戳 **Oct 13**，源 **Oct 16**（不同步） |

| 备份 | ❌ **KV 与 `api/` 数据无备份/恢复脚本** |

**为什么这是地基问题：**

- **19MB 的 `training_dataset.json` 贴着 25MB 上限**，且它是**数据管线中间产物**——它该不该出现在公开静态站上？**没有人做过这个判断。** 一次数据增长就会撞上限，而撞上限的表现是**部署失败**（不是告警）。

## 3. 最危险的三条（必须先修，且不能拖）

### 🔴 D1 · 线上 `/api/data.json` 正在提供过期且自相矛盾的数据

- **现状**：`curl https://roboparts.cc/api/data.json` → 767 条 / 2026-08-27；文件内 `total_entities` 却写 868；站点 404 页、定价页、**全部文章页脚**都把它当"868 条完整数据集"外链。
- **为什么必须立刻修**：这是**公开可被一次 curl 证伪**的矛盾。任何潜在合作方、审稿人、Agent 抓到它，整个项目的"诚实"人设就崩了——而"诚实"正是这个项目**唯一的核心卖点**。
- **修法**（1 天内）：
  1. 决定 `data.json` 是**弃用**还是**继续维护**。二选一，不要模糊。
  2. 若弃用 → 全站外链改指 `/api/entities.json`，并在 `_headers` 加 301 重定向；`data.json` 从部署目录移除。
  3. 若继续维护 → 把它纳入 `regen_derived.py` 的重生成链，**并在闸门里加"`data.json.meta.entity_count == entities.json.count`"**。
- **验收判据**：`curl -s https://roboparts.cc/api/data.json`（或重定向后的端点）返回的实体数 **等于** `entities.json.count`；新增闸门 `对外数据集端点实体数一致`。

### 🔴 D2 · 单一真相源没有一致性闸门，且自身不自洽

- **现状**：`entities.json` 三个 `updated` 不等；三份副本结构不同；108 个脚本写 `api/`；16 个产物过期。
- **修法**（1–2 周）：
  1. **统一时间戳**：`entities.json` 只保留**一个** `meta.updated`，其余字段由 `regen_derived.py` 注入；加闸门断言"文件内只有一个时间戳字段且各处相等"。
  2. **建产物依赖图**：在 `scripts/pipeline/registry.py`（已存在）里登记每个产物的**生产者脚本 + 上游产物**；新增 `scripts/check_freshness.py`——任一产物 `generated_at` 早于其上游 ⇒ 判红。
  3. **消灭或收编副本**：`data.json` / `data.js` 要么删，要么变成**带校验的派生物**（生成时把 `entities.json` 的 sha256 写进自己的 meta，闸门比对）。
- **验收判据**：新闸门 `产物依赖图新鲜度（上游早于下游即判红）` + `实体副本 sha256 对账`；`entities.json` 时间戳唯一。

### 🔴 D3 · 最强验证不可复现

- **现状**：`regression.py` 11,430 行、只在本地、依赖被 gitignore 的 `ops/`。
- **修法**（2–4 周，这是硬骨头）：
  1. **切分**：把 `regression.py` 按"是否需要 `ops/`"拆成两半——**仓内可判定部分**（进 CI）与**运营留痕部分**（明确标注"仅维护者本地"）。
  2. **把 `ops/` 的依赖脱敏**：凡是"棘轮/留痕/日报纪律"这类断言，改为读**仓内快照**（如 `ops-snapshot/` 里的最小样本），让外部人可复现。
  3. **让 CI 跑全量**：`ci.yml` 增加一步 `python scripts/regression.py --ci-subset`。
- **验收判据**：**在一个全新的 `git clone` 里，只跑 `npm ci && npm run ci`，能复现 100% 的绿灯**——不需要任何私有目录、任何凭据。

## 4. 为"楼建得更高"预埋的结构（安全 / 稳定 / 可扩展）

上一份报告提了 L1–L5 五个跃迁（组合演算、装配级检查、Agent 原生、证据飞轮、标准位）。**这些跃迁每一个都在往地基上加荷载。** 以下是**必须在跃迁之前**埋好的结构，否则楼越高越危险：

| 预埋结构 | 服务于哪个跃迁 | 为什么现在就要有 |
|---|---|---|
| **版本化 API 契约 + 弃用策略** | L3 Agent 原生 | Agent 会**缓存**你的接口契约。字段一改，下游 Agent 静默失效。没有版本头 = 每次改动都是一次隐性破坏 |
| **证据账本的事务性与幂等** | L4 证据飞轮 | 账本是追加式的，但**并发写入 / 重放 / 去重**的语义未定义。飞轮一转起来，重复贡献会污染证据 |
| **求解器的资源边界** | L2 装配级检查 | `assemble(goal, set)` 是组合搜索。**没有超时与复杂度上限，一次恶意/退化输入就能打满运行时** |
| **审计日志（谁在何时调了什么）** | L3 + L5 | Agent 依赖你，就必须能回答"这个判定是什么时候、由谁、基于哪版数据做出的" |
| **多租户数据隔离** | L5 标准位 | 一旦厂商上传自己的目录跑 conformance，**隔离与防越权**就是硬要求 |
| **Schema 演进策略（版本 + 迁移）** | 全部 | 80 个产物 + 2 个 schema，任何一次结构变更现在都是**破坏性**的 |
| **灾备（KV + api/ 快照）** | 全部 | 积分、API key、供应商数据**无备份 = 单点全损** |
| **性能预算** | 全部 | `entities.json` 1.8MB / `training_dataset.json` 19MB 每次全量加载——**性能预算是地基的一部分** |
| **供应链安全（lockfile + SBOM）** | 全部 | 根目录无 lockfile ⇒ 任何人 `npm i` 拿到的依赖都可能不同 |

**一句话**：**L1–L5 是"楼"，第 4 节这张表是"地基的承重结构"。先埋承重，再盖楼。**

## 6. 诚实边界

1. **本报告基于静态扫描 + 线上回探，未做压测、未做渗透测试。** §2.4 的安全项是**配置级发现**，不是漏洞评估结论。
2. **F1（线上 data.json）已用 `WebFetch` 回探确认**（`entity_count=767` / `generated_at=2026-08-27`）。其余"线上"判断未逐条回探，因为本地 `curl` 在本环境受限。
3. **"1:111 测试比例"是行数比，不是覆盖率。** 行数比低不必然等于覆盖差（有些断言在生成脚本里），但**在没有覆盖率测量的情况下，无法证明覆盖好**——这个"无法证明"本身就是问题。
4. **`regression.py` 11,430 行里可能有相当比例是"数据/文案断言"而非"逻辑断言"**，拆分时需逐段判断，本报告未做逐行分类。
5. **阶段划分是按依赖关系排的，不是按工作量。** 1.2（验证重构）与 1.3（测试框架）**互相依赖**，实际可能必须并行推进，无法严格串行。
6. **本报告不主张"停止盖楼"。** 主张是：**阶段 0 立刻做，阶段 1 与 L1–L5 并行做，阶段 2/3 在盖楼之前埋好。**

## 7. 一句话收束

> **项目在"引擎层"做到了罕见的严谨——三态 fail-closed、阴阳自证、变异评分。**
> **但"产物层"和"分发层"是 fail-open 的：谁都能写一份 `api/*.json`，没人知道它过期了，也没有闸门拦它。**
>
> **最危险的组合，是精密的引擎 + 过期的输入。** 它会算出一个看起来可信的错答案，
> 而 60 道闸门里没有一道管这个。
>
> **先把地基建到和引擎一样严谨，再往上盖。**
> **阶段 0（线上止血）本周做；阶段 1（依赖图 + 验证重构 + 测试框架 + 数据契约）本月启动；
> 阶段 2/3（前端、安全、灾备、承重结构）在 L1–L5 盖起来之前埋好。**
>
> **地基不牢时，"再加一层能力"不是进步，是把风险往上叠。**
